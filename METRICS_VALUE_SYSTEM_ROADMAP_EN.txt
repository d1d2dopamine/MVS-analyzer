METRICS VALUE SYSTEM
Origin, scientific rationale, development stages, and desktop application roadmap

Document status: Concept and development roadmap
Date: July 18, 2026
Project author: D1D2DOPAMINE

======================================================================
1. HOW THE BENCHMARK LED TO THE METRICS VALUE SYSTEM
======================================================================

The RT Variability Benchmark was originally created to compare reaction-time variability metrics: SD, CV, MAD, IQR, MAD/median, and IQR/median. Its initial question was straightforward: which metric performs best when group differences are evaluated under outliers, missing responses, and unequal trial counts?

The completed simulations showed that no metric is universally superior.

With clean data, SD and CV detected weak differences effectively. Under outliers, their sensitivity decreased sharply, while outliers affecting only one group could create false group differences. MAD and IQR were more resistant to outliers, but sometimes had lower sensitivity to very small effects. When groups differed in average response speed, absolute measures of spread could indicate a difference even when relative variability was equal, whereas CV, MAD/median, and IQR/median behaved more appropriately. Random missingness generally had little effect, but preferential loss of slow responses could strongly distort nearly every metric.

This produced a new conclusion: the task is not to select one “best” metric or to average all available measures. The operating characteristics of every metric should be evaluated under conditions resembling the dataset being analyzed.

This led to the Metrics Value System: a simulation-calibrated framework for context-dependent metric evaluation.

======================================================================
2. CORE CONCEPT
======================================================================

The Metrics Value System does not declare any metric absolutely correct. It estimates how each metric typically behaves under conditions similar to those of the analyzed dataset.

Instead of ambiguous labels such as “Reliability” and “Reason,” the system uses measurable operating characteristics:

- Estimated Power;
- Estimated False-Positive Rate (FPR);
- Normalized Bias;
- Between-seed Standard Deviation;
- Benchmark Coverage;
- Contextual Performance Score;
- Diagnostic Flags.

The system must not claim that errors are impossible. It should report estimated operating characteristics, uncertainty, and applicability boundaries.

======================================================================
3. DEFINITION OF A DATA REGION
======================================================================

A region is not an individual millisecond or an arbitrarily selected part of the results. A region is a data state described by a set of characteristics:

- number of participants;
- number of trials per participant;
- reaction-time distribution;
- skewness and right-tail length;
- outlier rate;
- outlier magnitude;
- missing-response rate;
- missingness mechanism;
- dependence of missingness on response speed;
- difference in average speed between groups;
- proportion of participants with insufficient data;
- assumed effect magnitude;
- inequality of trial counts.

If tasks, blocks, or groups within one dataset differ substantially in data quality, they may be evaluated as separate states. Segmentation must never depend on where a desirable p-value was obtained.

======================================================================
4. VALUE SCORE FORMULA
======================================================================

A simple arithmetic average of components is not appropriate. High sensitivity must not compensate for an excessive false-positive rate or severe bias.

The initial structure will therefore be multiplicative:

Value Score =
100 × Coverage × Sensitivity Component × Calibration Component
    × Bias Component × Between-seed Consistency Component

Each component ranges from 0 to 1. If a critical component approaches zero, the total score decreases sharply.

The formula does not use the p-value obtained from the study being analyzed. Otherwise, metric selection could be adjusted toward a preferred result.

Before the formula is adopted, the project must:

1. prespecify all components and transformations;
2. develop the formula using the training simulation grid;
3. freeze its parameters;
4. evaluate it on held-out scenarios;
5. publish the formula and its limitations.

======================================================================
5. BENCHMARK COVERAGE AND UNUSUAL DATASETS
======================================================================

No scientifically defensible formula can be guaranteed to work on every unknown dataset. The system therefore requires Benchmark Coverage.

A new dataset is represented as a vector of characteristics and compared with the evaluated simulation grid. Coverage decreases as the dataset moves farther from tested states.

Example output:

Benchmark Coverage: 0.91
Domain status: within evaluated domain

or:

Benchmark Coverage: 0.22
Domain status: outside evaluated domain
Automatic scoring suppressed

When Coverage is too low, the application must not produce confident metric weights. It should suspend automatic ranking and identify which characteristics fall outside the benchmark domain.

======================================================================
6. SCIENTIFIC DEVELOPMENT PLAN
======================================================================

STAGE 0. Stabilize the RT Variability Benchmark

- rename the technical label null to no_difference;
- preserve the validated v1.2.0-rc1 results;
- freeze the final configuration;
- rerun the benchmark after the technical correction;
- release the stable v1.2.0 benchmark.

STAGE 1. Build a large data-state space

Create a space-filling sample of data states together with dedicated extreme stress tests. A full Cartesian product will not be used because it would generate millions of redundant combinations.

Planned dimensions include:

- 20–160 participants;
- 20–320 trials;
- multiple effect magnitudes;
- lognormal, gamma, and ex-Gaussian distributions;
- 0–10% outliers;
- multiple outlier magnitudes;
- random and RT-dependent missingness;
- differences in average speed;
- unequal trial counts.

STAGE 2. Evaluate all metrics

Every supported metric will be run in every selected state. Simulations will use multiple seeds. Runs must be resumable: the application or command-line tool should save intermediate results instead of restarting a long computation after interruption.

STAGE 3. Build the operating-characteristics database

For every state–metric pair, store:

- Estimated Power;
- Estimated FPR;
- Normalized Bias;
- Between-seed Standard Deviation;
- valid-participant rate;
- sensitivity to outliers;
- sensitivity to missingness;
- Monte Carlo uncertainty intervals.

STAGE 4. Construct the Contextual Performance Score

The formula will be developed only on a prespecified training subset of the simulation space. All coefficients, penalties, and thresholds will be documented. Once held-out scenarios have been inspected, any change to the formula requires a new version.

STAGE 5. Estimate Benchmark Coverage

Develop a normalized distance between a new dataset profile and the simulation grid. Include both gradual Coverage decay and a hard outside-evaluated-domain threshold.

STAGE 6. Test on unseen scenarios

At least 20% of data states will be excluded from formula development in advance. They will be used to test:

- whether metrics are ranked appropriately;
- whether false detections are predicted;
- whether conclusions transfer across distribution families;
- whether the system handles unusual combinations of problems;
- whether the formula has overfit the original grid.

STAGE 7. Evaluate on open empirical datasets

The system will be applied to open reaction-time datasets. Its outputs will be compared with sensitivity analyses and known data characteristics. Empirical data will complement, not replace, simulation-based validation.

======================================================================
7. METRICS VALUE SYSTEM DESKTOP APPLICATION
======================================================================

A standalone Windows .exe is a logical delivery format. Users would not need to edit code, operate a terminal, or install Python manually. This would increase the project’s practical value and strengthen its role in a scientific and technical portfolio.

The application must not replace the open-source implementation. The scientific core should remain inspectable and testable, while the .exe provides an accessible interface to that core.

Proposed architecture:

MVS Core
- formulas and calculations;
- data profiling;
- benchmark database;
- Contextual Performance Score;
- Benchmark Coverage;
- Diagnostic Flags;
- reproducible reports.

RT Variability Adapter
- reading RT datasets;
- identifying participant, group, condition, and RT columns;
- calculating RT metrics;
- evaluating outliers and missingness;
- matching data profiles to the RT benchmark.

Desktop GUI
- drag-and-drop CSV/TSV import;
- column assignment and confirmation;
- data preview;
- one-click analysis;
- metric operating-characteristics table;
- visualizations;
- Diagnostic Flags;
- report, CSV, JSON, and PNG export;
- version, configuration, and seed logging.

An initial implementation may use Python, PySide6, and PyInstaller. This would preserve the existing Python core while producing a standalone Windows executable. Linux and macOS versions may follow after stabilization.

======================================================================
9. WHAT THE APPLICATION MUST NOT DO
======================================================================

- guarantee that a result is correct;
- describe a metric as true or absolutely reliable;
- conceal individual results behind a single composite score;
- assign weights based on observed p-values;
- make automated medical or diagnostic claims;
- produce a score when Benchmark Coverage is insufficient;
- upload user data without explicit consent;
- change the scoring formula without a version change.

Analysis should be local and offline by default.

10. VERSIONING PLAN
======================================================================

The application version and benchmark version must be recorded separately in every report.

======================================================================
11. EXTENSION TO OTHER DOMAINS
======================================================================

The system core may be general, but every domain requires a separate adapter, metric set, and benchmark.

Potential architecture:

MVS Core
- RT Variability Adapter;
- Dataset Quality Adapter;
- Algorithm Comparison Adapter;
- Medical Metrics Adapter;
- Machine Learning Adapter;
- Reproducibility Adapter.

RT-derived scores cannot be transferred automatically to medicine or machine learning. The general element is the framework: measurement of operating characteristics, Coverage estimation, overfitting control, and transparent limitations. Domain-specific formulas and simulations must be validated independently.

======================================================================
12. PRACTICAL VALUE
======================================================================

For researchers:
- less arbitrary metric selection;
- transparent comparison of conflicting measures;
- automated sensitivity analyses;
- reproducible material for Methods and Limitations sections.

For algorithm developers:
- evaluation of metric behavior across data states;
- identification of conditions that create false signals;
- comparison of versions without blindly averaging performance measures.

For the D1D2DOPAMINE project:
- progression from a standalone benchmark to an independent methodological system;
- a practical open-source tool;
- integration of simulation, statistics, user experience, and reproducibility;
- a substantial scientific and technical portfolio project.

======================================================================
13. CONCISE DEFINITION
======================================================================

The Metrics Value System is a simulation-calibrated framework for estimating the context-dependent operating characteristics of analytical metrics. It replaces blind single-metric selection and unweighted averaging with transparent evaluation of sensitivity, false detections, bias, between-run variation, and proximity to an evaluated benchmark domain.

The MVS desktop application is intended to make this framework accessible without code editing while preserving open algorithms, reproducible calculations, and explicit applicability boundaries.
