# Полный исходный проект Round37: порядок в корне

Это полный проект, а не патч. Исходники, тесты, workflow и встроенный Colab-архив включены. Документы поставки теперь находятся в `packaging/`, а не рядом с папкой проекта в ZIP.

В корне осталось 15 файлов и 23 каталога вместо 17 и 25. Четыре папки исходников плагинов собраны в `plugins/sources/`, два готовых пакета — в `plugins/packages/`. Важные файлы README, решения/проекта, лицензии, безопасности, настроек и Windows-ресурсов остались на месте. Это умеренная уборка без перемещения рабочего ядра и проектов.

## Если распаковываешь поверх существующего репозитория

Самый безопасный вариант — сначала распаковать ZIP в новую отдельную папку и сравнить с рабочим репозиторием. Наложение полного ZIP само может перезаписать локальные правки ещё до запуска помощника: скрипт защищает перенос старых плагинов, а не всю процедуру распаковки. Сначала отдельно сохраните все локальные изменения и остановите программы, которые пишут в проект.

ZIP сам не удаляет старые файлы. После обычной распаковки старые шесть записей останутся в корне, пока ты их явно не перенесёшь. Не удаляй их вслепую: там могут быть твои изменения.

1. Сохрани текущую рабочую копию и посмотри `git status`.
2. Скопируй содержимое папки `MVS-analyzer-main` из ZIP в корень существующего проекта. Не вкладывай эту папку ещё на один уровень.
3. Из корня проекта выполни проверку без изменений:

   `python tools/migrate_root_layout.py`

4. Если проверка показывает ожидаемые шесть старых записей и отсутствие конфликтов, выполни явное применение:

   `python tools/migrate_root_layout.py --apply`

Скрипт проверяет цифровые отпечатки всех новых и старых файлов по `packaging/root-layout-migration-v1.json`. Изменённый файл, лишний файл внутри старой папки, отсутствующее/другое новое содержимое или ссылка вызывают отказ до переноса. Он ничего не удаляет: старые корневые записи перемещаются в уникальную папку `.mvs-layout-backup/`. При сбое переноса уже перемещённые записи и журнал сохраняются; автоматического перезаписывающего отката нет. Подробный вывод указывает, где лежит каждая копия. Если обнаружен конфликт, сохрани свои изменения отдельно и сопоставь их вручную; не обходи проверку заменой хешей.

5. Проверь `git status` и изменения. Для Git перемещение обычно выглядит как удаление старого пути и добавление нового, после добавления файлов Git распознаёт совпадение содержимого. Добавляй нужные изменения выборочно; `.mvs-layout-backup/` в коммит не включай. Скрипт сам Git не меняет и коммит не создаёт.
6. Запусти `python tools/check_source.py`, затем свои обычные CI-проверки. Полный `python tools/test_root_layout.py` проверяет также точный состав чистого корня поставки: запускай его на свежей распаковке. Личные заметки или дополнительные рабочие папки могут вызвать отказ этой проверки состава; сам мигратор такие посторонние корневые записи не удаляет и не переносит.

Старые корневые файлы должны исчезнуть именно из будущего коммита, иначе GitHub продолжит их показывать. Резервная папка остаётся локально доступной для ручного восстановления. Перед восстановлением убедись, что старый путь свободен; не перезаписывай новые пользовательские изменения.
