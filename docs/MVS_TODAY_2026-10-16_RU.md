# MVS: что сделано 16 октября и где остановиться

## Что это значит для тебя

- Стало труднее незаметно перепутать исходные данные и результаты: хеш, то есть цифровой отпечаток файла, теперь относится к действительно прочитанным байтам.
- Восстановление из сохранённого расчёта (checkpoint) исправлено для двух воспроизводимых ошибок. Старые ответы, повторно используемые из кеша, не считаются надёжными при неизвестной среде вычисления.
- При сбое записи видно, какие файлы действительно удалось сохранить. Текущий этап исключает старые чужие файлы из результатов нового запуска.
- Исправлена наша ошибка упаковки Colab и усилена проверка, чтобы устаревший вложенный исходник не проходил сдачу незамеченным.
- Два статистических улучшения проверены, но не включены: они не прошли заранее установленные условия. Рабочие формулы не менялись.
- Научный NO-GO означает, что пока нельзя объявлять MVS подтверждённо пригодным для исследовательских выводов. Успешные инженерные тесты этого не заменяют.
- Сегодня заканчиваем текущий этап и передаём полный ZIP. Для Windows ещё нужен реальный повторный запуск исправленных проверок владельцем.

## План завершения сегодняшней работы

1. Закрыть текущую ошибку Round36: старые файлы в папке с `--overwrite` не должны приписываться новому успешному запуску. Сами старые файлы сохраняются.
2. Проверить исправление на воспроизводимом старом сбое, чистом контрольном запуске, CLI и Python; сохранить исходные результаты и независимую проверку.
3. Собрать полный исходный проект, распаковать в новую папку и выполнить проверки встроенного Colab-исходника, исторических хешей и соответствующих контрактов.
4. Передать полный ZIP и этот итог. Следующий этап сегодня автоматически не начинается.

Окончательные результаты Round36 и проверки архива приведены в `ROUND36_OVERWRITE_PROVENANCE_RU.md` и `../validation/round36-results.json`. Исправление подтверждено исходным контрпримером и повторными проверками CLI/Python; полный исходный ZIP проходит отдельную финальную проверку после распаковки перед передачей.

## Что стало надёжнее

### Входные данные действительно соответствуют указанному хешу (Round25)

Раньше программа сначала читала CSV, а потом отдельно открывала путь для вычисления хеша. Если файл успевал измениться, расчёт относился к одним байтам, а запись об исходных данных — к другим. Теперь активные CLI/benchmark-пути получают наблюдения, сведения об импорте и хеш из одного захвата исходных байтов. Проверены замена файла после захвата, кодировки/BOM, независимость двух импортов и совпадение численных результатов на стабильном входе. Это исправление происхождения данных, а не повышение статистической мощности. Старые Desktop/Remote-пути остаются отдельно обозначенной границей.

Доказательства: отчёты Round25 и их сохранённое сравнение; первый замер с параллельной нагрузкой не скрыт и не выдан за контролируемый замер.

### Исправлен код по Windows-ошибкам; повторная Windows-проверка ещё нужна (Round26)

Предоставленные пользователем журналы показали, что завершение всех процессов Job Object ещё не гарантирует, что основной процесс уже доступен как завершённый. Исправлено ожидание обоих условий в пределах одного срока. Нестабильная проверка ACL через PowerShell заменена независимым небольшим .NET-проверяющим инструментом. Linux-тесты и разбор кода не заменяют повторный запуск настоящей Windows CI: этот пункт ещё открыт.

### Восстановление вычислений стало безопаснее в двух конкретных случаях (Rounds29–30)

При ошибке первой записи выбранная точка восстановления раньше терялась внутри текущего сеанса. Теперь можно повторить попытку в том же сеансе после устранения причины записи, сохранив выбор и сведения о среде.

Дополнительно воспроизведён более серьёзный случай: после записи и повторного запуска старое значение функции оптимизатора из другой среды принималось за актуальное. Контрольный пример возвращал −999 без вычисления вместо правильного 1. Теперь смешанная или неизвестная история среды заставляет пересчитать значения функции в сохранённом симплексе. При известной той же среде быстрый путь сохранён. Проверены отдельные процессы, повторные открытия, неизвестная история и сходимость; независимый повтор дал 1 после двух вычислений. Цена — повторные вычисления при сомнительном происхождении кеша. Это не обещание идентичности всех результатов между средами и не полная транзакционность резервных копий.

### Расчёт меньше зависит от конкретного способа сохранения (Round31)

Пять вычислительных входов получили явный передаваемый на один запуск интерфейс записи. Поэтому ошибки записи, отмену и порядок событий можно проверять без изменения математического алгоритма. Старые публичные вызовы продолжают пользоваться прежней реализацией. Сравнивались результаты, последовательности записи и кеши, а не только факт успешной сборки.

Это улучшение проверяемости архитектуры. Замеры скорости смешанные, некоторые короткие сценарии стали медленнее; общего ускорения не доказано.

### Файлы после ошибки и после повторного использования папки описываются честнее (Rounds33–34,36)

При частичной ошибке экспорта CLI раньше мог скрыть уже сохранённые полезные файлы. Добавлен учёт завершённых записей и явный неполный результат. Затем тот же контракт распространён на восстановленные небенчмарковые вычисления. Ошибочный запуск по-прежнему остаётся ошибочным; сомнительный недописанный файл не выдаётся за проверенный.

Round36 закрывает соседний случай успешного `--overwrite`: в новый манифест и список результатов попадал чужой старый файл из этой папки. Старый дефект подтверждён реальным CLI: научные файлы полностью совпадали с чистым запуском, но старый файл был ошибочно подписан как часть нового результата. Исправление ограничивает принадлежность файлами текущей записи, а Python учитывает явно объявленную область списка. Итоговые проверки текущего исправления перечисляются в отдельном отчёте Round36.

Граница остаётся: это не единая атомарная операция на всю папку. Старый неинструментированный benchmark-экспорт не получает новых гарантий автоматически.

## Что мы узнали о статистике, но не включили в рабочий метод

### Эксперимент с общей перестановочной проверкой (Rounds27–28)

В фиксированном наборе разработки новый вариант чаще обнаруживал два заданных изменения: 31,6% и 50% против 14% и 28,8% у сравниваемого рабочего варианта. Однако на основном тяжёлохвостом нулевом условии было 19 срабатываний из 200, то есть 9,5%; заранее заданная проверка допустимости не пройдена. Поэтому вариант не активирован.

Независимое восстановление тех же 999 перестановок для всех 200 основных нулевых случаев не нашло расхождений вычисления. Это исключает проверенные ошибки реализации, но не превращает результат в успешную калибровку и не доказывает, что избыток был случайным. Новые выборки для «спасения» результата не добавлялись. Расход времени выше: около 5,08 раза для самой проверки и 1,53 раза вместе с общей подготовкой в этом эксперименте.

### Прямое применение готовой Math.NET-функции (Round32)

Изолированная замена хвоста нормального распределения повысила точность в центральной области, но не прошла все заранее заданные строгие требования и бюджет микрозамера. 170 отклонений относились к крайне малым числам на границе представимости; это не 170 практических ошибок исследований. Все пять несовпадений решений на специально построенных пороговых точках присутствовали и у прежнего варианта, новых относительно него не было; одно зависит от различия точной арифметики и округлённого правила сравнения.

Прямая замена не включена. Этот опыт не доказывает превосходство самописной математики или непригодность готовых библиотек. Он показывает, почему версия, округление, пороги и стоимость должны рассматриваться вместе. Замер 4,45-кратного замедления относится к одной короткой математической операции, а не ко всему MVS.

## Отдельно: собственный долг поставки, а не новые возможности

В Round33 был передан устаревший встроенный Colab-архив исходников. Пользователь обнаружил реальный сбой CI. В Round34 архив пересобран официальным генератором, а точная команда `python tools/check_source.py` проверена также после свежей распаковки полного ZIP. Это исправление нашей ошибки упаковки.

Более широкая Colab-проверка выявила 17 устаревших исторических привязок исходников. Round35 сохранил старые исходные хеши и добавил явный проверенный слой изменений: 13 переходов подтверждены сохранёнными материалами, четыре старых пробела происхождения честно оставлены пробелами. Для текущих версий выполнен разбор кода. Неизвестное изменение теперь должно быть отвергнуто, а не автоматически принято пересчётом хеша. Это контроль рассмотренного исходника, не научная сертификация.

При финальной проверке Round36 также исправлено смешение отрицательных тестовых примеров с обычными CI-результатами: намеренно повреждённые манифесты теперь хранятся отдельно и не ломают строгую проверку корректных выходов. Это ещё одно закрытие нашего долга интеграции проверок, а не новая статистическая возможность.

В Round36 новый разрешённый переход добавляется следующим отдельным слоем; старая история не переписывается.

## Идём ли в правильную сторону и насколько быстро

Есть несколько доказанных улучшений, влияющих на достоверность работы: соответствие данных хешу, корректное восстановление кеша, видимость частичных файлов и исключение чужих старых результатов. Изменение интерфейса записи облегчает дальнейшие точные проверки. При этом производственные статистические формулы сегодня не стали «точнее»: два численных эксперимента дали основания не включать предложенные замены.

Количество этапов и тестов не является мерой скорости разработки. Часть времени ушла на воспроизведение редких сбоев и независимое сравнение; часть — на исправление собственного долга упаковки и проверок. Общее ускорение программы не установлено. Полезный итог — конкретные устранённые ошибки с сохранёнными отрицательными примерами и более ясные границы уверенности.

## Что остаётся и один следующий приоритет

- Настоящая Windows-проверка исправленного ручного workflow и отдельный запуск на Windows11 пользователя ещё требуют результатов владельца.
- Научный статус проекта остаётся NO-GO; успех инженерных проверок его не меняет.
- Непокрытые границы старого benchmark-экспорта, части архивных Desktop/Remote-входов и полных кешированных результатов остаются явно ограниченными.

Следующий приоритет после сегодняшней остановки — закрыть фактический пользовательский путь Windows MCP по результатам исправленного workflow: это целевая платформа пользователя и проверяемый критерий готовности, а не ещё один придуманный эксперимент. Если журнал покажет конкретный сбой, следующий этап должен быть ограничен его воспроизведением и исправлением. До получения такого результата нельзя объявлять Windows готовой.
