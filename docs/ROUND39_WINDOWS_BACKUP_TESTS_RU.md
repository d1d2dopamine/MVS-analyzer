# Round39: переносимость проверок аварийного сохранения на Windows

## Что показали два присланных журнала

В обоих журналах: **181/188 тестов пройдено**. Не прошли одни и те же семь:
`Late archive publication failure preserves retriable checkpoint` и шесть
`Restored … provenance survives late failure and repeated disk reload`
(foreign, mixed, reverse, empty, current, current_repeated).
Сообщение каждого: `Access to the path is denied.`

Публичные сведения о запуске
[38955858018](https://github.com/d1d2dopamine/MVS-analyzer/actions/runs/38955858018)
показывают сбой шага native core / сборки в windows-2022 и windows-2025.
Следующие проверки ACL, Job Object и настоящего MCP были пропущены. Коммит
`621ebde9f48348391bd9425ff213919359cb74f8` содержит изменения уровня Round36;
сами рассматриваемые тесты сохранились в Round38.

## Причина и точность диагноза

Эти тесты специально создают **папку** с именем `MVS_Backups.zip`, чтобы
сохранение общего архива завершилось ошибкой после записи отдельной контрольной
точки. Затем они должны проверить сохранность состояния и возможность повтора.
Старое ожидание перехватывало только `IOException`. Windows при попытке
`File.Move` поверх папки может вернуть `UnauthorizedAccessException`.
В таком случае тест прекращался раньше проверок состояния.

Присланные журналы содержат только текст сообщения, **без типа исключения и
стека**. Поэтому точный тип на машине GitHub не был непосредственно прочитан.
Диагноз основан на совпадении всех семи мест отказа, исходном пути вызова
`Begin → Flush → Store → ExportAll → File.Move` и реализации .NET:
[документация File.Move](https://learn.microsoft.com/en-us/dotnet/api/system.io.file.move?view=net-8.0),
[Windows FileSystem](https://github.com/dotnet/runtime/blob/v8.0.0/src/libraries/System.Private.CoreLib/src/System/IO/FileSystem.Windows.cs),
[преобразование ERROR_ACCESS_DENIED](https://github.com/dotnet/runtime/blob/v8.0.0/src/libraries/Common/src/System/IO/Win32Marshal.cs).
Окончательная проверка требует повторного запуска на Windows.

## Узкое исправление

Изменены только тестовые исходники. Для этой специально созданной папки
допускаются два **точных** типа исключения: `IOException` и
`UnauthorizedAccessException`. Папка обязана существовать до и после отказа.
Успешное сохранение не считается правильным исходом теста.

Все прежние проверки сохранённой контрольной точки, идентификатора, единиц
расчёта, pending restore, истории среды, повторного чтения и значений целевой
функции остались на месте. Ранние тесты другого препятствия — файла вместо
родительской папки — сохранили прежнее ожидание `IOException`.

Пять новых тестов проверяют оба допустимых типа, отказ при отсутствующей или
исчезнувшей папке, недопустимость успеха и передачу неожиданных исключений
без подмены. В том числе ошибки повреждённых данных, отсутствующего каталога
и отмена **не** принимаются за нужный отказ сохранения.

Производственные исходники, научные методы, встроенный Colab-пакет, строгие
source pins и Windows workflow с обязательными 21 проверкой не меняются.
Это исправление переносимости самого проверочного кода; оно не означает,
что работа MCP на Windows уже подтверждена.

## Выполненные проверки

На Linux / .NET 8.0.31 прошли **200/200 native-тестов**. Независимо выполнены
41/41 целевая проверка, включая отрицательные примеры классификации исключений.
Source pins: 64/64; Colab: 48/48; UI-структурные: 18/18; layout: 59/59;
release bundle: 35/35. Проверки исходного пакета, CLI-контракта и notebooks
также прошли. Сопоставлены 83 неизменённых файла производственного кода,
сборки, README, workflow, встроенного пакета и pin-манифестов.

Итоговые локальные результаты записаны в `validation/round39-results.json`,
сырые журналы и независимая проверка — в `validation/round39-evidence.zip`.
Старые неудачные Windows-журналы сохранены, а не заменены новыми Linux-результатами.
Новые синтетические исключения проверяют классификатор ошибок, но не имитируют
полное выполнение Windows.

## Следующее действие на Windows

Применить полный исходный ZIP, проверить собственные изменения и закоммитить
исходники. Затем запустить **Manual Windows workflow acceptance** на этом коммите.
Нужен успешный результат обоих заданий windows-2022 и windows-2025, включая
21 Win32-проверку без пропусков и последующие настоящие native/MCP проверки.
При повторной ошибке сохранить журналы упавшего шага. Windows 11 на компьютере
пользователя также остаётся отдельной проверкой. Научный NO-GO не меняется.
