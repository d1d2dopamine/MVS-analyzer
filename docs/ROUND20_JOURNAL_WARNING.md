# Round 20: machine-readable journal-write warning

## Reproduced gap and compatibility

Round 19 fixed journal location, but an actual journal-file obstruction still
showed a provenance warning only on stderr. The saved analysis was valid and
returned exit 0, yet automation reading the existing JSON diagnostics could not
see that the local journal had not been updated. The unchanged round-19 executable
reproduces that gap in the retained evidence.

The CLI now adds one existing-schema diagnostic when journal append fails:

```json
{
  "level": "warning",
  "code": "journal_write_failed",
  "message": "Analysis artifacts were saved, but the local run journal could not be updated."
}
```

The warning contains **no journal path, exception details, input values or user
identifier**. Existing stderr error detail is retained for local troubleshooting.
Artifact paths already required by the machine protocol are not removed or falsely
claimed anonymous. Other data warnings remain unchanged and in their existing order.

Analysis remains `status=completed`, `exitCode=0`, `error=null`, with its normal
saved artifacts. Missing provenance recording is not relabeled a scientific
failure. Python already exposes structured diagnostics; no wrapper implementation
change is needed. `allow_diagnostic=False` still rejects exit-2 scientific outcomes,
not completed analyses carrying warnings. Clients should inspect diagnostics even
for exit 0. The warning is runtime response metadata, not a new manifest field.

## Scope and rollback

The complete round-19 ZIP is the rollback point. Production changes are limited
to the existing journal exception handler in `MvsAnalyzer.Cli/HeadlessRun.cs`.
A focused Python regression and an opt-in actual CLI/Python tool are added, with
reports and evidence. The embedded portable source is regenerated by its existing
builder. Core calculations, journal format/resolver, method versions, schemas,
saved calibrations, defaults and scientific acceptance thresholds are unchanged.
The scientific development result remains **NO-GO**.

### Preserved tool-development failure

The initial audit tool expected the entire diagnostics array to be empty on the
old baseline. The actual response correctly already contained `data_warning`
about exchangeability. That attempt is retained. The final tool checks only the
new warning code and independently requires every other diagnostic to remain
identical. No production warning was removed and no scientific threshold changed.
The corrected sequence is run once; there is no seed or convergence tuning.

## Limits

The obstruction fixtures run on Linux. Windows/macOS, distributed filesystems and
concurrent journal writes are not newly validated here. A warning does not repair
a failed write, authenticate a journal or make output transactional. Completed
artifact manifests do not themselves carry this new runtime diagnostic; retain
the machine response if provenance-write status must travel with exported results.
