# Round40: полезные журналы при ошибке проверки

## Зачем это нужно

В присланных Windows-журналах была фраза `Access to the path is denied.`,
но не было типа исключения, стека вызовов и вложенной причины. Из-за этого
приходилось восстанавливать вероятный путь отказа по исходному коду.
Кроме того, один шаг Windows workflow объединял core-тесты и публикацию CLI;
его название не показывало, какая из двух команд остановилась.

## Что изменено

Только тестовый исполнитель и CI-диагностика:

- Старые строки `PASS`, `FAIL` и итог `N/M tests passed` сохранены.
- После `FAIL` добавляется `DETAIL` с обычным .NET-представлением исключения:
  типом, сообщением, доступным стеком и вложенным исключением.
- Проверки продолжаются после отдельного отказа; любой отказ сохраняет код
  завершения 1. Успешный набор сохраняет код 0.
- Windows core-тесты и публикация CLI теперь имеют разные шаги. Завершившаяся
  команда записывает фиксированное имя и свой код в отдельный `*-status.json`
  перед передачей ненулевого кода workflow. Эти файлы входят в артефакты.
- Отдельная контролируемая проверка запускает тестовый процесс с заведомой
  вложенной ошибкой, требует именно exit 1, проверяет детали и выполнение
  следующей проверки. Её намеренный отказ не подменяет настоящий набор тестов.

Нет дампа переменных окружения, `Exception.Data` или состояния модели.
Сообщения и стек самого исключения могут содержать пути и текст, переданный
кодом, поэтому перед публичной пересылкой журналы всё равно следует просмотреть.
Стек есть лишь там, где .NET действительно располагает им; он не выдумывается.

## Границы

Производственные расчёты, сохранение данных, формулы, строгие source pins,
встроенный Colab-пакет и все критерии научной готовности не меняются.
Round39 и организация корня сохранены. У Windows workflow остаются обязательными
21 Win32-проверка без пропусков и настоящие native/MCP проверки.

PowerShell-изменения проверены по исходному коду; локального Windows/pwsh
исполнения здесь нет. Linux-проверки репортера не являются Windows-проверкой.
Новая версия не отменяет уже запущенную пользователем сборку или workflow.

## Результаты

Linux/.NET: **205/205 native-тестов**; контролируемый отдельный процесс
действительно завершился с кодом 1 и сохранил вложенные причины и стек.
Независимо: 11/11 проверок репортера, 26/26 проверок workflow/CLI-контракта;
Python-валидатор: 5/5. Fresh Release-сборка: 0 предупреждений и ошибок.
Source pins: 64/64; Colab: 48/48; UI-структурные: 18/18; layout: 59/59;
release bundle: 35/35. Сопоставлены 82 неизменённых файла производственного
кода, сборки, README, встроенного пакета и pin-манифестов.

Фактические локальные проверки перечислены в `validation/round40-results.json`,
сырые журналы и независимый разбор — в `validation/round40-evidence.zip`.
Полный исходный ZIP проверяется после свежей распаковки. Научный NO-GO сохраняется.

Во время этой работы завершились оба пользовательских запуска на коммите

По публичным данным GitHub оба успешны. На windows-2022 и windows-2025 успешны
все шаги, включая Win32, калибровку и native/MCP parity. Идентичность исправления
Round39 и его workflow подтверждена по blob-хешам коммита. Защищённые сырые
журналы не скачивались; это проверка публичных результатов заданий и шагов.

Это результат предыдущего workflow, а не исполнение новых диагностических
изменений Round40 на Windows. Работа на личной Windows 11 пользователя и
научная пригодность для подтверждающего исследования — отдельные вопросы.
